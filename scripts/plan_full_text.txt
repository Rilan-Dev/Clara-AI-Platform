 1. Purpose, Scope & How to Use This Plan
 This document is the execution companion to the Feature Gap Analysis and AI Enhancement Roadmap. The
 gap analysis answered the question of what is missing; this plan answers the question of how to build it, in
 what order, and how to prove each piece is finished. Every one of the 55+ identified gaps and 10 catalogued
 defects is carried forward here as a workstream with an implementation approach, a data-model impact, and
 an acceptance test. Nothing from the analysis is dropped, and nothing new is invented: the sole purpose of
 this document is to convert findings into a stable, sequenced engineering programme that a small full-stack
 team can execute week by week.

 The plan is organised into four phases. Phase 0 is a two-week stabilisation sprint that closes the reported
 defects and installs the engineering baseline. Phase 1 builds the metering, audit, and enforcement core that
 every later capability depends on. Phase 2 lifts answer quality and trust: hybrid retrieval, reranking, inline
 citations, conversation memory, abstention, and the feedback loop. Phase 3 extends distribution and
 enterprise readiness: the embeddable widget, tool calling and MCP, live connectors, the evaluation harness,
 and the enterprise pack. Each phase is independently shippable, so the platform improves continuously rather
 than waiting for a monolithic release.

 1.1 Conventions used in this plan
 Workstreams are identified as WS-nn within their phase (for example WS-1.3 is the third workstream of
 Phase 1). Every workstream carries an effort score of S, M, or L, relative to a team of two to four full-stack
 engineers. Acceptance criteria are written as verifiable statements and collected into the QA matrix in
 Chapter 7; a workstream is done only when its acceptance criteria pass in a deployed environment, not when
 the code merges. Code fragments are given as reference implementations: they use Prisma schema syntax
 and TypeScript-style pseudocode and are meant to be adapted to the actual codebase, not pasted blindly.

 The reference stack assumed throughout is the one observable from the product itself: a Next.js full-stack
 application with TypeScript, Prisma over PostgreSQL, OpenAI-compatible model providers, pgvector or an
 equivalent vector index for retrieval, and Razorpay for billing. Where a component name is referenced
 (route handlers, middleware, dashboard components), the names are descriptive and should be mapped onto
 the real files during Phase 0 codebase orientation. No assumption is made about infrastructure provider;
 deployment targets are treated as interchangeable.

 1.2 Sequencing principles
   • Measurement before capability. Meters, audit records, and quota enforcement land before any new AI
       feature, because a capability that cannot be metered cannot be sold, supported, or defended.

   • Trust before reach. Citations, abstention, and feedback land before distribution channels (widget,
       tools), because every new channel multiplies the cost of an untrustworthy answer.

   • Server-side enforcement, always. Plan limits and feature gates are checked in API route handlers and
       middleware; hiding UI elements is a convenience, never the control itself.

   • Append-only records for billing and audit. Usage events and audit logs are immutable facts, never
       updated in place, so disputes and investigations reconstruct history rather than trust a mutable counter.

   • Weekly release train. Every phase is sliced so that something demonstrable ships each week behind
       feature flags, keeping risk small and progress visible.

 2. Phase 0 — Stabilisation Sprint (Weeks 1-2)
 Phase 0 exists because five defects were reported against the running product, and every one of them is
 either a trust risk or a revenue risk: knowledge base uploads fail intermittently, non-dashboard pages do not
 meet the mobile standard the dashboard set, the embedding model console offers a chat model where an
 embedding model belongs, the requests-today meter reads zero, and subscription limits are not enforced. The
 last two are architectural and therefore belong to Phase 1; the first three are fixable inside two weeks and are
 scheduled here. Phase 0 also installs the engineering baseline — continuous integration, a staging
 environment, and migration discipline — because every subsequent phase assumes a safe place to land code.

 The sprint is intentionally overloaded with quick, high-visibility work. Closing the upload bug restores
 confidence in the core ingest path; the mobile sweep makes the whole product feel finished on phones,
 which is where most evaluation traffic arrives; and the model catalogue fix removes a trap that could silently
 corrupt retrieval for any organisation that touches it. All four workstreams ship behind ordinary pull requests
 with their acceptance tests attached, so the sprint doubles as the first full exercise of the new release pipeline.



 2.1 WS-0.1 Engineering baseline (effort M)
 Set up GitHub Actions to run lint, typecheck, unit tests, and a production build on every pull request, with
 the same pipeline gating pushes to main. Provision a staging environment that mirrors production
 configuration, including the database, object storage, model provider keys, and Razorpay test mode, so that
 acceptance tests exercise real integrations rather than mocks. Adopt migration discipline: every schema
 change ships as a forward-compatible Prisma migration, and migrations run as a deploy step, never by hand.
 Install structured logging and an error tracker (for example Sentry) with source-map upload, and create a
 shared feature-flag service so later phases can dark-launch safely. The baseline is finished when a broken
 pull request cannot merge, and a green pull request can be promoted to staging and then production with one
 command each.

   • Acceptance: a deliberately failing test blocks merge in CI; a trivial change deploys to staging and
       production via pipeline only; an injected error appears in the tracker with stack trace and affected user
       within one minute.

 2.3 WS-0.3 Mobile responsiveness sweep (effort M)
 The dashboard already meets the mobile standard and serves as the reference. Extract its effective rules into
 design tokens — a spacing scale, a type scale, a minimum interactive control height of 44 pixels, 16-pixel
 page gutters, and card gap minimums — and encode them once in the shared theme. Then sweep every
 remaining surface: the landing page first (it is the first thing a prospective customer sees on a phone), then
 auth screens, agent builder tabs, KB management, billing pages, and the platform admin console. The sweep
 is executed against a fixed device matrix (a small phone at 360 pixels, a standard phone at 390, a large phone
 at 430, and a tablet at 768) and verified with both screenshots and automated viewport tests, so regressions
 are caught by CI rather than by customers. Component-level fixes — oversized fonts, oversized inputs,
 missing card gaps — are corrected in the shared components, not per page, so the fix propagates everywhere
 at once.

   • Acceptance: no horizontal scroll at 360 pixels on any route; every interactive element at least 44 by 44
       pixels; Lighthouse mobile accessibility and layout-shift scores of 90 or better on the landing and top five
       dashboard routes; the device-matrix screenshots are attached to the pull request as review evidence.



 2.4 WS-0.4 Model catalogue correction (effort S)
 The model console currently permits selecting gpt-4o-2024-08-06 — a chat model identifier — as the
 embedding model, and warns about vector dimension matching without being able to enforce it. The
 correction splits the single model list into two catalogues: chat models (the gpt-5.6 family, gpt-4o variants)
 and embedding models (the text-embedding-3 family), each entry carrying its provider, context or token
 limits, cost per million tokens, and — for embedding models — the output dimension. Selections are
 constrained to the correct catalogue, and a dimension mismatch between the selected embedding model and a
 knowledge base becomes a hard, explained error rather than a warning. The full re-indexing workflow that
 safely re-embeds existing chunks when the embedding model changes is a Phase 2 workstream (WS-2.8);
 Phase 0 only makes bad states unrepresentable in the console.

 3. Phase 1 — Metering, Audit & Enforcement Core
 (Weeks 1-4)
 Phase 1 fixes the platform's two architectural defects and lays the spine that every later feature hangs from.
 The requests-today meter reads zero because chat completions evidently never write usage events; the fix is
 not a patch on the counter but an append-only usage-event pipeline that records every billable model
 invocation. Subscription limits can be bypassed because enforcement lives in the interface rather than the
 API; the fix is a quota middleware that checks plan limits server-side before every billable action. Audit
 logging of user prompts and AI answers, which today exists nowhere, is built on the same event spine, giving
 platform admins a complete record and organisation dashboards the user-question visibility that was
 requested. Streaming responses and organisation analytics parity complete the phase, so that by week four
 the platform counts everything it does, refuses what plans do not allow, and shows both to the right people.



 3.1 WS-1.1 The usage-event pipeline (effort M)
 Every billable AI invocation — a chat turn, an embedding batch, a transcription, later a text-to-speech
 render — appends one immutable row to a UsageEvent table. The row records who, what, and how much:
 organisation, user, agent, knowledge base, the model called, prompt and completion token counts, latency,
 and an estimated cost computed from the model catalogue's price list. Writes happen in the same request

 lifecycle that performs the model call, and rows are never updated or deleted; corrections are new
 compensating rows. Meters then stop being guessed state and become simple aggregations: requests-today is
 a count over today's window in the organisation's timezone, monthly usage is a count over the billing period
 anchored to the Razorpay renewal date, and storage is a sum over document bytes. A nightly rollup job
 pre-aggregates daily totals per organisation so dashboards read one small table instead of scanning the event
 log.

 3.2 WS-1.2 Server-side quota enforcement (effort M)
 A quota middleware wraps every billable route handler. It resolves the caller's organisation and plan, loads
 the plan's limit matrix, and checks each applicable limit atomically — either a transactional count against the
 usage-event window or a maintained counter incremented in the same transaction that admits the request, so
 concurrent requests cannot race past a limit. When a limit is exceeded, the API returns 402 with a
 machine-readable code, a friendly message, and an upgrade call-to-action payload; the client renders the
 upgrade sheet from that payload rather than from its own guess. At 80 percent utilisation, the middleware
 emits a soft-warning event that the client surfaces as a dismissible banner. Feature gates — model access,
 connectors, SSO — are checked in the same layer, because a capability hidden in the UI is not enforced; the
 API must refuse it too.


    Reference implementation — quota middleware (TypeScript pseudocode)

    export async function withQuota(req, plan, orgId) {
      // 1. feature gate: is this capability in the plan at all?
      if (!plan.features.includes(req.feature)) {
        throw new ApiError(403, 'PLAN_FEATURE_UNAVAILABLE', upgradeCTA(req.feature));
      }
      // 2. usage gate: atomic check-and-increment on the billing window
      const used = await db.$transaction(async (tx) => {
        const n = await countWindow(tx, orgId, req.limitKey, windowBounds(plan));
        if (n >= plan.limits[req.limitKey]) {
          throw new ApiError(402, 'QUOTA_EXCEEDED', upgradeCTA(req.limitKey));
        }
        if (n + 1 === Math.floor(0.8 * plan.limits[req.limitKey])) {
          emitSoftWarning(orgId, req.limitKey, n + 1);
        }
        return n + 1;
      });
      return used;
    }
    // Every billable handler: const used = await withQuota(...); then model call,
    // then usageEvent append — the append is mandatory and sits in finally-style
    // bookkeeping so failures still bill honestly if the provider charged.

 Two classes of bypass are explicitly closed. First, direct API calls: every enforcement point in Table 4 is
 testable with a raw HTTP client and no browser, and the acceptance tests do exactly that, because a quota
 that only holds when the UI behaves is not a quota. Second, concurrency: the check-and-increment runs
 inside a database transaction, so one hundred simultaneous requests against a plan with one remaining credit
 admit exactly one request and refuse ninety-nine. Rate limiting per user and per IP is layered above plan
 quotas as a separate abuse control, so a single user on an unlimited plan still cannot flood the platform.



 3.3 WS-1.3 Plan-by-plan validation matrix (effort S)
 The platform owner asked for each plan to be validated one by one, deeply, with blocking, warnings, error
 messages, and hiding all behaving properly. This workstream builds that validation as a permanent test suite
 rather than a one-off manual pass, so every future plan change is automatically re-verified. For each plan
 tier, a seeded organisation is created with its limits set near the boundary; scripted request loops then walk
 each limit to exactly N, N plus one, and beyond, asserting the refusal, the message copy, the meter accuracy,
 and the upgrade path at each step. UI-level tests assert the hiding and locking behaviour for plan-gated
 features, and API-level tests assert that hidden features are refused even when called directly.

 3.4 WS-1.4 Audit logging of prompts and answers (effort M)
 Audit logging records every user prompt and every AI-generated answer as a first-class, immutable fact,
 visible to platform admins and — in a privacy-preserving, question-only form — on organisation dashboards.
 The AuditLog row captures the actor, organisation, agent, knowledge base, conversation, and message
 identifiers, the full prompt and answer text, the model, token counts, a redaction field listing what was
 masked, and a tamper-evident hash chain: each row hashes its content together with the previous row's hash,
 so any after-the-fact modification breaks the chain visibly. Writes share the transaction that persists the
 message, so an answer can never exist unlogged. A redaction layer masks emails, phone numbers, and
 payment identifiers by default; platform admins with a recorded justification can reveal the original, and the
 reveal itself is audited. Retention is tiered: ninety days hot and searchable, one year in cold archive, with
 organisation-configurable shortening but never lengthening past the compliance cap.

 4. Phase 2 — Answer Quality & Trust (Weeks 5-12)
 Phase 2 makes the assistant's answers measurably better and visibly trustworthy, and it builds the loop that
 keeps them improving after launch. The retrieval layer is upgraded from pure vector similarity to hybrid
 search with reranking, which the RAG literature consistently ranks as the highest-leverage quality change
 available to a production system. Answers gain inline citations that open the exact source passage, so
 verification is one click instead of one investigation. Conversations become first-class objects with memory,
 follow-up questions, and shareable history. The assistant learns to abstain honestly when the knowledge base
 cannot support an answer, and every abstention becomes a content-gap signal. Users gain thumbs feedback
 that routes unhappy conversations to a review queue. Knowledge-base owners get a retrieval playground to
 see exactly what the system would retrieve, and the embedding-model migration workflow makes model
 changes safe. Voice output completes the voice loop that voice input began.



 4.1 WS-2.1 Hybrid retrieval and reranking (effort L)
 Hybrid search combines two retrievers that fail in complementary ways. Dense vector search captures
 meaning but misses exact identifiers — product codes, error numbers, names that embed poorly; keyword
 search (BM25 over PostgreSQL full-text indexes) nails those exact tokens but misses paraphrase. Both run
 per query, their ranked lists are fused with Reciprocal Rank Fusion, and a second-stage cross-encoder
 reranker (a hosted reranking model or a self-hosted bge-family reranker) reorders the fused top-k into the
 final top-n that reaches the prompt. Query rewriting resolves pronouns and ellipses against the conversation
 history before retrieval runs, so "summarise that second point" retrieves the right documents; multi-query
 expansion optionally issues two or three reformulations for ambiguous questions and merges their results.
 The whole pipeline is behind a per-KB feature flag and evaluated on the golden set before default-on,
 because a retrieval change that is not measured is a regression waiting to ship.

    Reference implementation — Reciprocal Rank Fusion (TypeScript pseudocode)

    function rrfFuse(listA, listB, k = 60) {
      // listA: BM25 ranked chunk ids; listB: vector ranked chunk ids
      const scores = new Map();
      for (const [rank, id] of listA.entries()) {
        scores.set(id, (scores.get(id) ?? 0) + 1 / (k + rank + 1));
      }
      for (const [rank, id] of listB.entries()) {
        scores.set(id, (scores.get(id) ?? 0) + 1 / (k + rank + 1));
      }
      return [...scores.entries()]
        .sort((x, y) => y[1] - x[1])
        .map(([id]) => id);
    }
    // top-k per leg (k = 20) -> fuse -> rerank to top-n (n = 6) -> prompt context



   • Acceptance: on the golden set, recall@10 improves by at least 15 percentage points over the vector-only
       baseline; identifier-heavy queries (codes, exact names) that failed before now retrieve their source;
       rerank adds under 300 milliseconds at p95; the pipeline flag can revert retrieval to vector-only in one
       configuration change without a deploy.

 4.3 WS-2.3 Conversation memory and controls (effort M)
 Conversations become first-class persisted objects: a sidebar lists them with rename and pin; each

   • Acceptance: follow-up questions resolve correctly across at least five turns of pronoun references;

 4.4 WS-2.4 Abstention policy and no-answer analytics (effort S)
 When fused retrieval confidence is low — below a per-KB threshold on the reranker's scores — the assistant
 abstains with an honest, templated response: it states that the knowledge base does not appear to contain the
 answer, shows the closest things it did find, and suggests either asking differently or requesting that the
 document be added. Abstention replaces the hallucination failure mode with an actionable gap, which is
 precisely the behaviour procurement reviewers probe for. Every abstention is recorded as an event, so the
 organisation dashboard's content-gap report ranks the questions the KB could not answer — a ranked
 backlog of what to ingest next, derived from real user intent rather than guesswork.

   • Acceptance: on a KB that lacks the answer to golden-set unanswerable questions, the assistant abstains in
       at least 95 percent of cases instead of fabricating; abstention rate is a first-class metric on org and admin
       dashboards; the content-gap report aggregates per KB and per week.

 4.7 WS-2.7 Retrieval playground and chunk inspection (effort M)
 Knowledge-base owners gain a playground: type a question, see the exact chunks the retriever would fetch,

   • Acceptance: playground results match production retrieval bit-for-bit for the same query and KB state;
       chunk deletion takes effect in production retrieval immediately; the re-chunk preview requires no write

 4.8 WS-2.8 Embedding-model migration and re-index workflow (effort M)

 one-click rollback restores the previous index without data loss. The workflow records the embedding model
 identity and dimension on each KB, and queries refuse to run against a dimension-mismatched state — the
 enforcement point Phase 0's catalogue fix prepared.

 6.2 API conventions
 All new endpoints follow one error contract so clients can render failures uniformly. Quota and feature
 refusals use 402 and 403 respectively with machine-readable codes and an upgrade payload; validation
 failures use 422 with a field-annotated payload; unexpected failures use 500 with a correlation identifier that
 also appears in the server log line. Every billable endpoint accepts an idempotency key so retries after
 network failures cannot double-charge a quota, and list endpoints paginate with stable cursors rather than
 offsets so quota suites and analytics consumers get consistent reads. Rate limits are communicated through
 standard headers, and the widget's public endpoints additionally validate origin and embed key before any
 per-visitor logic runs.

 6.4 Security and privacy baseline
 Multi-tenant isolation is enforced at the data layer: every query path includes orgId scoping, and a CI lint rule
 fails any raw database access that omits it. Secrets live in the platform secret store, never in the repository,
 and rotate on a schedule. The OWASP LLM Top 10 is the checklist for AI-specific risks: prompt-injection
 hardening (retrieved content is data, never instructions; tool calls are permissioned and audited), output
 filtering, and PII redaction on both prompt and answer sides of the audit log. Encryption in transit
 everywhere and at rest for storage and database volumes, and a penetration test before the enterprise pack
 goes generally available, close the baseline.



 6.5 Testing pyramid
 Unit tests cover services and pure functions; integration tests cover API routes against a real database and the
 provider abstraction in record-replay mode; end-to-end Playwright tests cover the user-visible flows of every
 phase, including the quota suites from WS-1.3 and the mobile device matrix from WS-0.3; and load tests
 exercise streaming under concurrency before each phase exit. The rule that keeps the pyramid honest is that
 every acceptance criterion in this document maps to at least one automated test that runs in CI, which is
 exactly what Chapter 7 tabulates.

 forward-compatible so rollback never requires data surgery; and the weekly release train means any given

 dominant load of its weeks and should not share a sprint with another L.

 9.1 The definition of stable
 Stable is a checklist, not a feeling. The platform is stable when all five reported defects are closed with their
 acceptance tests automated; when every plan tier's limits are enforced server-side and verified by the
 per-plan suites on each merge; when every prompt and answer is audited, redacted, and tamper-evident;

 when meters reconcile against the event log exactly for sampled organisations; when p95 first-token latency,
 provider error rate, and ingestion queue depth have stayed inside their budgets for thirty consecutive days;
 and when the nightly evaluation harness has gated releases for two weeks without a silent regression. At that
 point the platform counts what it does, refuses what plans forbid, proves what it answers, and watches
 itself — which is precisely what this programme was commissioned to achieve.



 9.2 Beyond the six months
 A short backlog is deliberately left for after the window rather than crammed into it: multi-language retrieval
 with language-aware chunking; a prompt A/B testing loop on top of the evaluation harness; agentic workflow
 orchestration beyond single tool calls; marketplace distribution of agent templates; and usage-based overage
 billing on top of the usage-event spine. Each of these becomes materially cheaper once Phase 3 lands, which
 is the sign of a well-sequenced foundation rather than an unfinished plan.
