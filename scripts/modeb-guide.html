Section 01
Overview — the two voice tracks

Clara AI Platform now runs two complementary voice architectures side by side, and they serve different purposes. Understanding which is which avoids most configuration confusion, because the two tracks have different prerequisites, different secrets, and different failure modes. The platform selects the track automatically based on the runtime mode reported by the voice session endpoint.

Track 1 — Pipeline mode (Mode A, already live)

The browser records short audio bursts and sends them to Clara's own REST endpoints: POST /api/voice/elevenlabs/transcribe (Scribe STT) → POST /api/embed/chat (RAG chat over SSE) → POST /api/voice/elevenlabs/tts (speech synthesis, pcm_16000). Every turn is a request/response cycle, so latency accumulates per sentence, but no extra secrets are needed. This is the mode used by the chat-window voice chat and by the embed voice demo today.

Track 2 — Mode-B agents (ElevenLabs Conversational AI, this guide)

A true real-time duplex conversation over a single WebSocket (wss://api.elevenlabs.io/v1/convai/conversation). The assistant listens, thinks, and speaks with sub-second responsiveness, supports interruptions, and — critically for the platform roadmap — can be attached to a phone number so the same agent answers real telephone calls. Because ElevenLabs' servers call back into Clara for knowledge retrieval and call analytics, this track requires the two security secrets this guide configures.

Section 02
Mode-B tool secret (ELEVENLABS_TOOL_HMAC_SECRET)

When a Mode-B agent is created, Clara registers a server tool (webhook tool) on the ElevenLabs agent so that every answer is grounded in your knowledge base. ElevenLabs' agents runtime calls that tool over HTTPS while the conversation is in flight:

The signed RAG callback flow
  • User speaks → ElevenLabs agent decides it needs knowledge-base context.
  • Agent calls POST /api/internal/elevenlabs/tools/rag-search on Clara, carrying an HMAC signature derived from the tool secret that Clara embedded in the agent's tool configuration at creation time.
  • Clara verifies the signature, runs hybrid RAG retrieval over the organisation's knowledge base, and returns the context chunk to the agent.
  • The agent speaks a grounded answer in real time — no browser round trips involved.

This is why the settings page marks the field as "Required before any Mode-B agent can be created": without the secret, Clara cannot sign the tool configuration, and the internal endpoint refuses every call. The secret never appears in the browser and never needs to be typed into the ElevenLabs dashboard — it stays server-side and is applied automatically when agents are created or re-synced.

Current status — already configured This secret was set up on 18 September 2026 using the platform's own settings API. It is a 64-character hexadecimal value (256 bits of entropy, above the 32+ character requirement), stored in platform_env_settings and masked in the UI. No further action is needed to satisfy the "Required before any Mode-B agent can be created" gate.
How to verify it is live

The internal tool endpoint reports its state through distinct error codes. Probing it with an unsigned request tells you exactly which stage of configuration is missing:

Verification — unsigned probe (safe, no side effects) curl -s -X POST https://clara.ai.amazetechclans.com/api/internal/elevenlabs/tools/rag-search \ -H "Content-Type: application/json" -d '{"query":"test"}' # Before the secret exists → HTTP 503 {"error":"Tool callback rejected (missing_secret)."} # After the secret exists → HTTP 401 {"error":"Tool callback rejected (missing_signature)."} # 401 missing_signature is EXPECTED for unsigned probes — it proves the secret is live.
How to set or rotate it later
1
Generate a fresh secret
Generate 64 random hex characters (well above the 32+ requirement) on any trusted machine: openssl rand -hex 32. Avoid reusing values from other services.
2
Save it through Settings → AI
Open Settings → AI → ElevenLabs → Mode-B tool secret, paste the value, and save. The UI stores it in platform_env_settings via a two-step confirmation flow and immediately masks it.
3
Re-sync existing agents
Rotating the secret invalidates the signature embedded in previously created Mode-B agents. After rotation, re-save or re-sync each agent so Clara re-writes the tool configuration with the new signature, then re-run the verification probe above.
Section 03
Post-call webhook secret (ELEVENLABS_WEBHOOK_SECRET)

After every Mode-B conversation ends — web session or phone call — ElevenLabs analyses the call and delivers a full report to your webhook endpoint: transcripts, timestamps, conversation analytics, and metadata. Clara receives these reports at POST /api/webhooks/elevenlabs/post-call and stores them as conversation records so organisations get call history without any browser involvement.

ElevenLabs signs every delivery with an HMAC signature header (ElevenLabs-Signature). The signing secret is generated by the ElevenLabs dashboard when you create the webhook — that is why this value, unlike the tool secret, must be copied from the dashboard into Clara. Clara additionally guards against replay attacks using a nonce store, so the same delivery can never be accepted twice.

Order matters Create the webhook in the ElevenLabs dashboard first — the dashboard generates and reveals the signing secret at that moment — then paste that secret into Clara. Doing it in reverse leaves you with a secret you cannot retrieve later without deleting and recreating the webhook.
Step-by-step setup
1
Open the ElevenAgents settings page
Sign in at elevenlabs.io, open Conversational AI / ElevenAgents, and go to its Settings page — direct link: https://elevenlabs.io/app/agents/settings. Post-call webhooks are configured workspace-wide here (they apply to all agents, including phone agents).
2
Register the webhook URL
In the Post-call webhooks section, add Clara's endpoint exactly as:
https://clara.ai.amazetechclans.com/api/webhooks/elevenlabs/post-call
3
Choose the webhook types
Enable post_call_transcription — it carries the full conversation data (transcripts, analysis, metadata) that Clara stores. Optionally add post_call_audio (base64 recording — large payloads) and call_initiation_failure (failure diagnostics for outbound/batch calls).
4
Copy the generated signing secret
When the webhook is created, the dashboard generates and displays its signing secret. Copy it immediately and store it in your password manager — it is the exact value Clara will need.
5
Paste it into Clara
Open Settings → AI → ElevenLabs → Post-call webhook secret, paste the dashboard value, and save. The field description in Clara ("Register the URL in the ElevenLabs dashboard") refers to steps 1–4 you just completed.
6
Verify end-to-end
Run a short test Mode-B conversation, then confirm the conversation appears in Clara's conversation history / call logs. Before setup, an unsigned probe of the webhook endpoint returns {"error":"Webhook rejected (missing_secret)."} with HTTP 503; after the secret is stored, unsigned probes are rejected as invalid-signature while genuine signed deliveries succeed.
Delivery behaviour to be aware of ElevenLabs requires webhook endpoints to answer with HTTP 200. Deliveries that repeatedly fail are auto-disabled after 10 consecutive failures (when the last success was more than 7 days ago or there never was one), and failed deliveries are retried automatically. If call history stops updating, check that Clara is reachable and that the stored secret still matches the dashboard value.
Section 04
First Mode-B agent & account tier

With both secrets in place, creating a Mode-B agent is a normal platform flow: an organisation opts into Conversational AI for one of its agents (knowledge base), acknowledges the ElevenLabs data-flow disclosure, and Clara provisions the ElevenLabs agent together with its signed RAG tool. The acknowledgement step exists because Mode-B sends conversation audio and transcripts through ElevenLabs' infrastructure — a deliberate, audited decision per organisation rather than a silent default.

Prerequisites checklist
  • ELEVENLABS_CONVERSATIONAL_AI_ENABLED is true (already set).
  • Mode-B tool secret configured (already done — Section 02).
  • Post-call webhook secret configured (Section 03 — the only outstanding item).
  • Restart the Next.js service once after toggling Conversational AI, so the documented CSP update for wss://api.elevenlabs.io is applied; realtime websockets already connect because wss: is present in the current policy.
  • The organisation's knowledge base is indexed and answers questions in pipeline mode.
The free tier will not carry production

The connected ElevenLabs account is currently on the free tier: 10,000 TTS characters per month (11% already consumed at verification time), only 3 custom voices, and instant voice cloning disabled. That is adequate for a first proof-of-concept conversation, but a single realistic testing session burns thousands of characters, and phone agents add their own consumption. Before exposing Mode-B to real users:

Exact quotas and prices change — confirm current limits at elevenlabs.io/pricing before committing. Character consumption is monitored on the platform side too: the credit alert threshold (ELEVENLABS_CREDIT_ALERT_THRESHOLD_PCT, currently 80%) emails super admins when the monthly budget approaches exhaustion.

Section 05
Phone calls with Twilio

Phone calls reuse the exact same Mode-B agents that power web conversations — the agent is simply attached to a phone number, and ElevenLabs bridges telephony audio to the conversation WebSocket. This is why the call centre of the platform's roadmap depends on Sections 02 and 03 being complete: the signed RAG tool keeps phone answers grounded, and the post-call webhook is what records every completed call back into Clara.

Two integration patterns
PatternHow it worksWhen to choose
ElevenLabs native Twilio integration You link your Twilio account (or import a number) in the ElevenLabs dashboard; ElevenLabs manages call media streams and binds the number to an agent. Recommended default. Least code, handles SIP/media, works with agent updates automatically.
Twilio Programmable Voice + agent API Your Twilio number's webhook tells Twilio to connect the call to the agent; optional "register call" flow for passing caller context. When you need custom IVR, routing logic, or CRM lookups before the agent picks up.
Platform-side settings

Clara stores telephony credentials per platform and per knowledge base in phone_call_configs. The platform-level fields currently sit under Settings → Phone and are empty today:

  • PHONE_PROVIDER — set to twilio (already configured).
  • TWILIO_ACCOUNT_SID — your Twilio Account SID (find it on the Twilio console dashboard).
  • TWILIO_AUTH_TOKEN — the matching auth token.
  • TWILIO_PHONE_NUMBER — the number callers dial (E.164 format, e.g. +94771234567).
Recommended wiring order
1
Buy / verify a Twilio number
In the Twilio console, purchase a number with voice capability in the country your callers dial from. For Sri Lanka / India deployments, confirm local number availability or use a regional Twilio subaccount.
2
Connect Twilio in the ElevenLabs dashboard
Follow the native integration guide (elevenlabs.io/docs/eleven-agents/phone-numbers/twilio-integration/native-integration) to link the account or import the number, then assign the number to your Mode-B agent.
3
Fill Clara's phone settings
Enter the SID, auth token, and number under Settings → Phone so the platform can place outbound calls and log per-KB call configuration.
4
Test inbound + outbound and confirm logs
Call the number, hold a short grounded conversation, then verify the call appears in Clara's call logs via the post-call webhook. SMS-based conversations and batch outbound calling are available as later extensions.
Billing reality check Telephony costs are separate from ElevenLabs character quotas: Twilio bills per minute per leg (inbound and outbound), and ElevenLabs bills conversation/character usage on top. Estimate combined per-minute cost before launching any call campaign, and keep the credit alert threshold enabled.
Section 06
Troubleshooting
The 403 "Origin is not in the allowed origins" error

This is the error the embed voice demo produced before 18 September. Every embed API key carries an allowed_origins list; the voice session endpoint compares the browser's Origin header against it and rejects mismatches with HTTP 403. The "Landing Demo" key had an empty list, so every origin — including the platform's own domain — was rejected. The key's cryptographic hash itself was valid (verified byte-for-byte), which is why the error message mentioned origins rather than an invalid key.

Fix applied on 18 Sep 2026 (equivalent SQL, for reference) -- Add the hosting origin to the embed key's allow-list UPDATE api_keys SET allowed_origins = ARRAY['https://clara.ai.amazetechclans.com'] WHERE key_prefix = 'clr_463c2914ca28'; -- "Landing Demo" key

For other keys that hit the same error (for example the "Rilan Test KBs" and "Production" keys also have empty origin lists today), either edit the key in the admin embed panel and add the exact origin including scheme and no trailing slash, or run the equivalent SQL above with the right key_prefix. A companion error, "Invalid or revoked embed API key", means the key value or its is_active flag failed instead — check the api_keys row.

Appendix B
Sign-out redirect fix

Signing out currently sends users to the login screen. The intended behaviour is a return to the public landing page. The sign-out handler lives in the workspace shell component that renders the profile menu (the same component builds the admin and org navigation). Its handler currently reads:

current handler (minified in production build) async function handleSignOut() { try { await logout(); } finally { router.push("/login"); } // ← change this line }
fix — send signed-out users to the landing page async function handleSignOut() { try { await logout(); } finally { router.push("/"); } // ← landing page }

Two details matter when applying this change. First, the same component also contains an authentication guard that redirects unauthenticated visitors away from protected pages — that guard (router.replace("/login") in a useEffect) must remain untouched, otherwise unauthenticated users could linger on protected shells. Second, if the org-facing workspace uses a second copy of the profile menu, apply the same one-line change there so both shells behave identically. Like Appendix A, this ships with the next code deployment.

How settings are saved (the two-step flow)

Every settings save in the UI — including both secrets — uses a confirmation-token flow that prevents cross-site request forgery. The browser first asks the API to mint a short-lived token bound to the new value, then commits the value by presenting that token:

two-step save (what the Settings UI does internally) # Step 1 — mint a confirmation token (valid 5 minutes) GET /api/platform/env?token=1&key=ELEVENLABS_WEBHOOK_SECRET&value=<secret> → { "confirmation_token": "…", "timestamp": 1789762372296, "expires_in_ms": 300000 } # Step 2 — commit POST /api/platform/env { "key": "ELEVENLABS_WEBHOOK_SECRET", "value": "<secret>", "confirmation_token": "…", "timestamp": 1789762372296 } → { "ok": true, "key": "ELEVENLABS_WEBHOOK_SECRET", "updatedAt": "…" }
Security hygiene for operators Secrets stored here are readable in plaintext from the database by anyone with SQL access — protect database credentials accordingly and rotate them on any suspicion of exposure. Prefer generating fresh secrets over reusing values from other tools, never paste secret values into chat tickets or emails, and treat the masked display in Settings → AI as the only appropriate place to confirm a secret's presence. The default admin account password should also be rotated before production hardening is considered complete.
