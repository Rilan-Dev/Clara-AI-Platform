# Mode-B Tool Secret & Post-Call Webhook Secret — Setup Guide

> Companion to [`Doc/ELEVENLABS_INTEGRATION.md`](./ELEVENLABS_INTEGRATION.md) (the full operator runbook).
> This guide is the step-by-step walkthrough for the **two secrets that gate Mode B
> (Conversational AI) and post-call analytics**. Read it once, keep it as reference.

Both fields live in **Admin → Settings → AI Configuration → Platform environment**
(the "Mode-B tool secret" and "Post-call webhook secret" fields). Values are
persisted in the `platform_env_settings` table and applied to the live process
**without a restart** — the settings page is the source of truth; `.env` is the
boot-time fallback.

| Secret | Field label | Env variable | Generated by | Protects |
|---|---|---|---|---|
| Mode-B tool secret | "Mode-B tool secret" | `ELEVENLABS_TOOL_HMAC_SECRET` | **You** (32+ random chars) | `POST /api/internal/elevenlabs/tools/rag-search` — the RAG server-tool callback ElevenLabs agents invoke during a live conversation |
| Post-call webhook secret | "Post-call webhook secret" | `ELEVENLABS_WEBHOOK_SECRET` | **ElevenLabs** (per-webhook signing secret) | `POST /api/webhooks/elevenlabs/post-call` — transcript/analytics delivery after every call |

Both are server-only: never `NEXT_PUBLIC_*`, never returned by any API, scrubbed
from logs (`src/lib/redact.ts`), and compared in constant time
(`crypto.timingSafeEqual`).

---

## 1. Mode-B tool secret (`ELEVENLABS_TOOL_HMAC_SECRET`)

### 1.1 What it is

When a Mode-B (Conversational AI) agent answers a question, its vendor-side
prompt calls a **webhook tool** named `clara_rag_search` that points back at the
platform:

```
ElevenLabs agent ──POST {query}──► /api/internal/elevenlabs/tools/rag-search
                                    headers: x-clara-tool-token: <the secret>
                                             x-clara-org-id / -kb-id / -agent-id
```

The ElevenLabs webhook-tool mechanism cannot compute per-request HMAC
signatures, so the platform uses a **static shared token**: the secret is baked
into the tool's `request_headers` when the agent is created
(`ElevenLabsVoiceProvider.createConversationalAgent`), and every callback is
verified against it. Tenant ids ride along as constant headers and are
re-validated against the `elevenlabs_agents` binding on every callback, so a
leaked tool config cannot retarget another tenant's knowledge base.

**Consequence of the "baked-in at creation" design:** if you rotate the secret,
existing Mode-B agent bindings keep calling with the OLD token → their RAG
callbacks start failing with `401 bad_signature`. After rotating, **re-create
the affected agent bindings** (org panel → delete + re-create).

### 1.2 Prerequisites (order matters)

1. `ELEVENLABS_API_KEY` is set (ElevenLabs dashboard → API keys).
2. `ELEVENLABS_ENABLED` = `true` — the master kill switch.
3. `ELEVENLABS_CONVERSATIONAL_AI_ENABLED` = `true` — the Mode-B opt-in.
   ⚠️ **This flag requires a process restart** — the CSP snapshots the vendor
   websocket origin per process. Flip it in the settings page, then restart the
   Next.js service once.

### 1.3 Generate the secret

Any of these produces a valid 32+ character random secret:

```bash
# Recommended — 64 hex chars of CSPRNG entropy
openssl rand -hex 32

# Alternatives
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
python3 -c "import secrets; print(secrets.token_hex(32))"
```

Rules of thumb:

- **32+ characters**, random, never a dictionary word or reused password.
- One secret per platform deployment (all orgs' Mode-B agents share it; the
  tenant boundary is the binding re-validation, not the secret).
- Store it in your password manager BEFORE pasting it anywhere — the settings
  field masks it and there is no "reveal" after save.

### 1.4 Set it in the platform

1. Sign in as a **platform (super) admin**.
2. Go to **Settings → AI Configuration → Platform environment**.
3. Find **Mode-B tool secret** (shows "Not set up yet" before the first save).
4. Paste the generated secret → **Save**.
   - The value is written to `platform_env_settings` and the live
     `process.env.ELEVENLABS_TOOL_HMAC_SECRET` — **no restart needed**.
   - `.env` on the server can carry the same value as a boot-time fallback; the
     DB row wins at boot (`syncEnvFromDb`).

### 1.5 Verify

The readiness gate answers immediately after saving. As a super admin, in the
browser console on the logged-in admin session:

```js
fetch("/api/admin/elevenlabs/agents?orgId=<org-id>", { method: "GET" })
  .then((r) => r.json())
  .then(console.log);
```

- Creating a Mode-B binding no longer refuses with
  *"ELEVENLABS_TOOL_HMAC_SECRET is not configured — Mode-B agents cannot be
  created without it."* → the secret is live.
- Direct callback probe (server-side, from the app host):

```bash
curl -i -X POST https://clara.ai.amazetechclans.com/api/internal/elevenlabs/tools/rag-search \
  -H "Content-Type: application/json" \
  -H "x-clara-tool-token: <YOUR SECRET>" \
  -d '{"query":"test"}'
```

| Response | Meaning |
|---|---|
| `401 {"failure":"missing_secret"}` | Platform secret not set (page not saved / wrong env) |
| `401 {"failure":"missing_signature"}` | Header missing — check the tool config on the agent |
| `401 {"failure":"bad_signature"}` | Secret mismatch — rotated? re-create the binding |
| `200` + RAG result or a tenant-binding `403` | Secret verified ✔ (a tenant 403 here is EXPECTED for a bare probe — ids missing) |

### 1.6 Rotation

1. Generate a new secret (§1.3).
2. Save it in the settings page (live immediately for verification).
3. **Re-create every Mode-B agent binding** — org's Mode B panel → delete the
   binding → create it again. Creation registers a fresh vendor tool with the
   new token; the old vendor tool keeps the old token and will fail
   `bad_signature` until deleted.
4. Optionally delete the orphaned `clara_rag_search` tools from the ElevenLabs
   dashboard (Conversational AI → Tools) to keep the workspace tidy.

## 2. Post-call webhook secret (`ELEVENLABS_WEBHOOK_SECRET`)

### 2.1 What it is

After every Mode-B conversation (voice session or phone call), ElevenLabs
delivers the transcript + analytics to the platform:

```
ElevenLabs ──POST──► /api/webhooks/elevenlabs/post-call
                      header: elevenlabs-signature: t=<unix_s>,v1=<hex HMAC>
                      where HMAC = SHA-256(secret, `${t}.${rawBody}`)
```

The secret is **generated by ElevenLabs per webhook** (you cannot choose it).
The platform verifies the signature with a ±10-minute timestamp window and a
nonce ledger (replay protection). A legacy plain-HMAC header is also accepted
for older vendor deliveries. Transcripts are PII-redacted **before** storage.

### 2.2 The callback URL

For production:

```
https://clara.ai.amazetechclans.com/api/webhooks/elevenlabs/post-call
```

The URL is derived from `NEXT_PUBLIC_APP_URL` — make sure it is set to the
public domain (`https://clara.ai.amazetechclans.com`) before provisioning.

### 2.3 Option A — automated provisioning (recommended)

The platform can create the webhook at the vendor AND capture the secret in one
super-admin call (`POST /api/admin/elevenlabs/webhooks`, implemented in
`webhooks.ts → postElevenLabsWebhookProvision`):

1. Sign in as a **platform (super) admin**.
2. In the browser console (same session):

```js
fetch("/api/admin/elevenlabs/webhooks", { method: "POST" })
  .then((r) => r.json())
  .then(console.log);
```

3. Expected result:

```json
{ "webhookId": "…", "url": "https://clara.ai.amazetechclans.com/api/webhooks/elevenlabs/post-call", "secretConfigured": true }
```

The signing secret the vendor returns is persisted straight into
`ELEVENLABS_WEBHOOK_SECRET` (via `setPlatformEnvSetting`) — verification picks
it up **without a restart**. The action is audited in
`subscription_audit_log` (`elevenlabs_post_call_webhook_provisioned`).

Notes:

- Re-running creates a **second** webhook at the vendor (provisioning is
  deliberately not idempotent). Remove stale "Clara post-call" webhooks from
  the ElevenLabs dashboard afterwards.
- If the response carries `"secretConfigured": false` + a warning, the vendor
  did not return the secret — continue with Option B manually.

### 2.4 Option B — manual (ElevenLabs dashboard)

Use this when automated provisioning is unavailable, or the vendor created the
webhook without returning a secret.

1. Open the **ElevenLabs dashboard** → workspace **webhooks** section
   (Conversational AI settings → Webhooks, or the workspace settings page).
2. **Add a webhook**:
   - URL: `https://clara.ai.amazetechclans.com/api/webhooks/elevenlabs/post-call`
   - Event: **post-call** (transcript/analytics delivery)
   - Name: e.g. `Clara post-call`
3. ElevenLabs displays the **signing secret** once — copy it immediately.
4. In the platform: **Settings → AI Configuration → Post-call webhook secret**
   → paste → **Save**. No restart needed.

### 2.5 Verify

1. Make a short Mode-B test call (org with an acknowledged Mode-B binding), or
   trigger a test delivery from the ElevenLabs dashboard if available.
2. Within a minute, the conversation appears in the org's Mode-B conversation
   history (`/api/voice/elevenlabs/conversations` surfaces the synced table).
3. If nothing lands, check the route response — failure codes:

| `401` failure | Cause | Fix |
|---|---|---|
| `missing_secret` | `ELEVENLABS_WEBHOOK_SECRET` not set on the platform | Save the secret (§2.4 step 4) |
| `missing_signature` | Delivery without `elevenlabs-signature` header | Webhook created without HMAC auth — re-create with auth_type hmac (Option A does this) |
| `bad_signature` | Secret mismatch | The dashboard secret ≠ platform secret — re-copy & save |
| `stale_timestamp` | `t=` older than 10 min | Clock skew or replay — investigate, do not widen blindly |
| `replayed_nonce` | Same delivery already processed | Expected replay protection; safe to ignore once |

### 2.6 Rotation

Delete the webhook in the ElevenLabs dashboard (or generate a new secret there),
then re-provision via **Option A** or re-copy via **Option B**. Old secrets stop
matching immediately — the nonce ledger keeps already-processed deliveries from
double-counting.

## 3. Full go-live checklist (both secrets + Mode B)

Order matters — each step unblocks the next:

1. ☐ `ELEVENLABS_API_KEY` set (Settings → AI Configuration).
2. ☐ `ELEVENLABS_ENABLED` = `true`.
3. ☐ `ELEVENLABS_CONVERSATIONAL_AI_ENABLED` = `true` **+ restart the app once**.
4. ☐ Generate + save **Mode-B tool secret** (§1).
5. ☐ Provision the **post-call webhook** (§2) — Option A preferred.
6. ☐ Per organisation: **Settings → Conversational AI (Mode B)** → acknowledge
   the data-flow disclosure → create the agent binding (this registers the
   vendor agent + `clara_rag_search` tool with the secret from §1).
7. ☐ End-to-end check: start a realtime voice session — it should resolve
   Mode B (`mode: "conversational"`); if Mode B refuses, the client
   automatically falls back to the Mode-A pipeline and logs the reason.
8. ☐ After a test call: confirm the transcript arrived (post-call webhook) in
   the org's conversation history.

## 4. Security properties (why these two secrets exist)

- **Documents never leave the platform.** Mode B sends only the per-turn
  question to the RAG tool and receives short grounded snippets — the KB itself
  is never shipped to ElevenLabs.
- **Server-only secrets.** Neither value is ever exposed to the browser, logged
  in plaintext, or returned by any API (status endpoints report only
  connected/not-connected).
- **Constant-time comparison** on both paths — no timing oracles.
- **Replay protection** on the vendor path (timestamp window + nonce ledger,
  `elevenlabs_webhook_nonces`), fail-closed.
- **Tenant re-validation** on the internal tool path — the org/agent binding is
  re-checked on every callback, so the shared secret alone is not a tenant
  boundary.
