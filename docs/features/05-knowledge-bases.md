# 05 — Knowledge Bases

> Clara AI Platform feature documentation · Domain: `knowledge-bases` + `admin` KB core + `/api/kbs` · Base: `feature/ai-core-from-doable-source @ 031279b4`

## 1. Definition & Purpose

A Knowledge Base (KB) is the tenant's container of knowledge: uploaded documents, scraped web pages, and their embedded chunks in Qdrant. This feature manages KB CRUD, per-KB API keys, per-KB AI overrides, KB analytics, phone bindings, and the embedding-index state that tracks whether a KB is aligned with the platform embedding default. It is the substrate every grounded answer (Feature 08) retrieves from, and the unit administrators reason about ("which KB is my agent using, is it indexed, who can query it via API key").

## 2. Business Logic

- **KB CRUD** — `/api/kbs/[kbId]` (GET/PATCH/DELETE) and `/api/kbs/all` (cross-KB listing for admin pickers); creation happens through the agent workspace (`/api/agents/[agentId]/kbs`). Each KB gets a Qdrant collection name generated by `generateCollectionName` (`admin/core/collections.ts:11`).
- **Documents** — `/api/kbs/[kbId]/documents` (list/upload), `.../[docId]` (detail/delete), `.../reprocess` + `reprocess-all` (re-run the pipeline, Feature 06), `.../chunks` + `.../chunks/[chunkId]` (chunk inspection + validated mutations).
- **API keys** — `/api/kbs/[kbId]/api-keys` (issue/list/revoke) + `/usage` (per-key metering); keys authenticate the public embed/search API (`embed-api-key-db.ts` resolves landing/demo keys at `:6`, `:31`, `:58`, `:73`).
- **AI overrides** — `/api/kbs/[kbId]/ai-overrides` set a KB-level embedding model override (migration `014_kb_ai_overrides.sql`) used by chat-triggered re-index when a KB was built on a different embedding.
- **Analytics** — `/api/kbs/[kbId]/analytics` surfaces query counts, source usage and freshness for the KB screen.
- **Embedding-index state** — `/api/kbs/[kbId]/embedding-index` reports current/desired embedding models, progress, Resume/Cancel and old-index cleanup. Re-index preserves the existing live Qdrant collection until an atomic completion swap; failed jobs retain internal diagnostics for platform support while the organisation API returns safe messages (`src/modules/knowledge-bases/api/embedding-index.ts`, `core/reindex.ts`, `core/public-processing-error.ts`). Operational Gemini quota failure is tracked in OPS-01 issue #300.
- **Phone binding** — `/api/kbs/[kbId]/phone` binds a phone number config so voice callers ground on this KB (Feature 16).
- **Qdrant deletion integrity (new)** — `vector-store-kb.ts` deletion path now fails closed when Qdrant deletion errors, never masquerading as success (commit `008c6df3`, test `vector-store-kb.deletion.test.ts`).

## 3. Business Rules

- Each KB has one **live** Qdrant collection, while re-indexing may temporarily build a separate target collection and retain an old collection for safe rollback/cleanup. Chunk reads/writes go through the vector-store-kb layer; the live index is not replaced until re-index completes.
- KB deletion must remove both the DB rows AND the Qdrant collection — a failed Qdrant deletion is an error, not a silent partial success (fail-closed rule, 008c6df3).
- API keys are the only unauthenticated access path and are scoped to a single KB with their own usage metering.
- Reprocessing is idempotent per document (status machine pending → processing → ready/failed, recoverable via Retry).
- KBs bound to a published agent deployment are snapshotted (Feature 04) — live edits affect drafts, not the pinned deployment collection.
- Deletion integrity is Qdrant-state-aware (FIX-01 @ ac7d945f): the document record is preserved when the vector collection is unavailable, delete is permitted only when Qdrant confirms the collection never existed, reindex mirrors are removed on document deletion, and scrape rollback deletes are scoped to the exact KB — never a cross-KB sweep.
- Chunk mutations are document-bound and validated (FIX-01 @ 031279b4): edits are bound to the owning document (cross-document chunk edits rejected), chunk indices are explicitly number-typed with clobbering prevented, and creation metadata is validated before any Qdrant write — malformed indices/payloads are rejected outright. Archived KBs (`status !== "active"`) are read-only for manual chunk creation/edits while cleanup paths remain available (`68720d97`/`86ff9eeb`, tests `9bbaea54`/`4ab92769`), and single-chunk reindex mirror deletion fails closed preserving the live point (`ff9f6771`, trusted KB identity bound into point deletion `e0d987c8`).
